# Internationalization (i18n) — Micro CRM

The app supports **English** and **Arabic**, with full RTL support for Arabic.

## Adding or changing a string

### 1. Update both message catalogues

Strings live in `messages/en.json` and `messages/ar.json`. **Both must always have identical key sets.** If one is missing a key or has an extra key, the build fails.

**To add a new string:**

1. Open `messages/en.json`
2. Add the key and its English value:
   ```json
   {
     "dashboard.title": "Dashboard",
     "dashboard.newCustomers": "New customers (12 months)"
   }
   ```

3. Open `messages/ar.json`
4. Add the same key with its Arabic translation:
   ```json
   {
     "dashboard.title": "لوحة التحكم",
     "dashboard.newCustomers": "عملاء جدد (12 شهراً)"
   }
   ```

5. Run the build to verify both catalogues have identical keys:
   ```bash
   npm run build
   # If keys don't match, the build fails with a clear diff
   ```

**To change an existing string:**

Update both `en.json` and `ar.json` with the same key.

### 2. Use the string in a component

#### Server Components

```typescript
// app/[locale]/dashboard/page.tsx
import { useTranslations } from 'next-intl';

export default function Dashboard() {
  const t = useTranslations();
  
  return (
    <div>
      <h1>{t('dashboard.title')}</h1>
      <p>{t('dashboard.newCustomers')}</p>
    </div>
  );
}
```

#### Client Components

Mark with `'use client'` and use `useTranslations()`:

```typescript
'use client';
import { useTranslations } from 'next-intl';

export default function CustomerForm() {
  const t = useTranslations();
  
  return (
    <button>{t('customers.create')}</button>
  );
}
```

### 3. Parameterized strings (e.g., "4 of 12 customers")

Use ICU message format with `{variable}` syntax:

**In messages/en.json:**
```json
{
  "customers.count": "{shown} of {total} customers"
}
```

**In messages/ar.json:**
```json
{
  "customers.count": "{shown} من {total} عملاء"
}
```

**In component:**
```typescript
const t = useTranslations();

<p>{t('customers.count', { shown: 4, total: 12 })}</p>
// Renders: "4 of 12 customers" (or Arabic equivalent)
```

### 4. Pluralization (optional)

ICU messages support plural rules. Example:

**In messages/en.json:**
```json
{
  "customers.updated": "{count, plural, one {# customer updated} other {# customers updated}}"
}
```

**In component:**
```typescript
const t = useTranslations();

<p>{t('customers.updated', { count: 1 })}</p>
// "1 customer updated"

<p>{t('customers.updated', { count: 5 })}</p>
// "5 customers updated"
```

## Locale routing & preference

- **Routes are locale-prefixed:** `/en/dashboard`, `/ar/dashboard` (configured in `i18n/routing.ts`)
- **Default locale:** English (`en`)
- **Preference storage:** Cookie `NEXT_LOCALE` (set by the language toggle)
- **Persistence:** Across sessions; cookie-based so the server can read it on the first request

When a user visits the root `/`, they are redirected based on:
1. Their stored `NEXT_LOCALE` cookie (if set)
2. Browser language preference (if no cookie)
3. Fallback to English

## RTL layout rules

The app uses **CSS logical properties only** — no `left`/`right` in the codebase. This ensures layouts mirror correctly under `dir="rtl"` without duplication.

### Logical properties

| Logical | Physical (LTR) | Physical (RTL) |
|---------|---|---|
| `inset-inline-start` | `left` | `right` |
| `inset-inline-end` | `right` | `left` |
| `margin-inline` | `margin-left` + `margin-right` | mirrored |
| `padding-inline` | `padding-left` + `padding-right` | mirrored |
| `text-align: start` | `text-align: left` | `text-align: right` |
| `text-align: end` | `text-align: right` | `text-align: left` |
| `border-inline-start` | `border-left` | `border-right` |
| `border-inline-end` | `border-right` | `border-left` |

**DO NOT use:** `left`, `right`, `margin-left`, `margin-right`, `padding-left`, `padding-right`, `border-left`, `border-right`. The build does not enforce this yet, but a review rejection will catch it.

### Regions that stay LTR even in Arabic

Per the prototype design and ADR-001, three regions remain `dir="ltr"` even when the rest of the page is `dir="rtl"`:

1. **Bar chart (new customers)** and its month labels (numbers do not mirror; "Jan", "Feb", etc. stay left-to-right)
2. **Revenue chart** axes and labels (numbers and currency symbols)
3. **Phone column** in the customers table (phone numbers do not mirror)

These regions are marked with `dir="ltr"` in the component. This is intentional.

## Font stack

- **English:** `Geist` (variable weight, 400–700)
- **Arabic:** `IBM Plex Sans Arabic` (400, 500, 600, 700)

Fonts are loaded in `app/layout.tsx` using `next/font`. The appropriate font is swapped at runtime based on the locale.

## Testing i18n

### Unit tests

All Vitest unit tests run against English by default. To test Arabic:

```typescript
// In your test file
import { render } from '@testing-library/react';
import { NextIntlClientProvider } from 'next-intl';
import messages_ar from '@/messages/ar.json';

test('Arabic message renders correctly', () => {
  const { getByText } = render(
    <NextIntlClientProvider locale="ar" messages={messages_ar}>
      <MyComponent />
    </NextIntlClientProvider>
  );
  
  expect(getByText('لوحة التحكم')).toBeInTheDocument();
});
```

### E2E tests

Playwright tests cover both locales. See `e2e/` for the full suite.

```typescript
// e2e/dashboard.spec.ts
import { test, expect } from '@playwright/test';

test.describe('Dashboard (EN/AR)', () => {
  test('English dashboard loads', async ({ page }) => {
    await page.goto('/en/dashboard');
    await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
  });

  test('Arabic dashboard loads with RTL', async ({ page }) => {
    await page.goto('/ar/dashboard');
    const html = await page.locator('html').getAttribute('dir');
    expect(html).toBe('rtl');
  });
});
```

## CI checks

The build fails if:
- `messages/en.json` and `messages/ar.json` have different key sets
- A component uses a key that doesn't exist in either file
- A message has an invalid ICU format

Run the checks locally:
```bash
npm run build
npm run typecheck  # Catches missing i18n keys
```

## Common patterns

### Conditional text (avoid `if` before `t()`)

❌ **Don't do this:**
```typescript
const message = isActive ? t('active') : t('inactive');
```

✅ **Do this:**
```typescript
// In messages/en.json:
// "status.isActive": "{isActive, select, true {Active} false {Inactive}}"

const message = t('status.isActive', { isActive });
```

### Dynamic keys (avoid runtime key construction)

❌ **Don't do this:**
```typescript
const key = `customer.status.${status}`;
const label = t(key);  // Build fails; key is unknown at compile time
```

✅ **Do this:**
```typescript
// In messages/en.json:
// "customer.status.active": "Active"
// "customer.status.inactive": "Inactive"

const label = t(`customer.status.${status}` as const);
```

### Dates and numbers

Use `Intl.DateTimeFormat` and `Intl.NumberFormat` for locale-aware formatting:

```typescript
const date = new Date('2025-11-15');
const formatter = new Intl.DateTimeFormat(locale, {
  year: 'numeric',
  month: 'long',
  day: 'numeric',
});
// EN: "November 15, 2025"
// AR: "15 نوفمبر 2025"

const number = 12345;
const numberFormatter = new Intl.NumberFormat(locale);
// EN: "12,345"
// AR: "12,345"
```
